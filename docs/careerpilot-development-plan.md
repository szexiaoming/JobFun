# JobFun → CareerPilot 产品与开发文档

> 文档状态：v1.0  
> 当前目标：把已有 JobFun 原型收敛为一个可演示、可验证、可逐步上线的 AI 求职产品。  
> 核心原则：所有匹配、改写和面试建议必须以用户真实经历为依据；系统可以指出缺口，但不能补造经历、技能、指标或结果。

## 1. 产品定义

### 1.1 产品名称

- 项目内部名称：JobFun
- 对外产品名称：CareerPilot
- 迁移策略：第一阶段保留 Python 包名和目录名，先修改产品文案与信息架构；公开发布前再统一仓库、域名和品牌名称。

### 1.2 一句话定位

**把一份招聘 JD 转化为有证据的匹配分析、可确认的简历行动和针对性的面试准备。**

英文副标题：From job descriptions to interview readiness.

### 1.3 目标用户

首版只服务一类核心用户：

- 正在申请技术、算法、数据或 AI 岗位的求职者；
- 已有一份可用简历和若干真实项目经历；
- 每次申请都需要理解 JD、调整表达并准备面试；
- 重视内容真实性，不希望 AI 编造项目或量化指标。

首版暂不专门服务招聘方、猎头、企业 HR 或完全没有简历内容的用户。

### 1.4 核心问题

1. JD 信息密集，用户难以快速区分硬性要求、加分项和岗位职责。
2. 普通匹配分数缺少依据，用户不知道分数为什么高或低。
3. AI 简历工具容易生成用户没有做过的事情，造成真实性风险。
4. 简历修改、面试准备和投递记录分散，无法围绕同一个岗位持续推进。
5. 用户做完分析后缺少明确的下一步行动。

### 1.5 核心价值

CareerPilot 的核心不是“生成更多文字”，而是建立下面这条可追溯链路：

```text
JD 要求
  ↓
真实经历证据
  ↓
匹配判断与不确定项
  ↓
用户确认
  ↓
简历行动 / 学习行动 / 面试行动
  ↓
投递与复盘记录
```

## 2. 产品原则

### 2.1 真实性优先

- 不得新增简历中没有依据的公司、项目、技能、数字、日期和成果。
- AI 找不到证据时必须标记为“无证据”或“需要用户补充”，不能自行推断为已掌握。
- 用户补充经历后，系统必须保留补充内容和确认记录。
- 改写前后都保留原文、建议文本、理由和来源证据。

### 2.2 证据优先于分数

总匹配分数只用于快速浏览，不能表述为录用概率。每个判断至少包含：

- 对应的 JD 要求；
- 匹配状态；
- 简历中的证据位置；
- 判断理由；
- 置信度或待确认标记；
- 推荐的下一步行动。

### 2.3 用户确认后执行

以下操作必须由用户确认：

- 将建议写入简历；
- 接受 AI 生成的经历补充；
- 创建或修改投递记录；
- 将状态改为已投递、面试、Offer 等；
- 未来接入日历、邮件或外部平台时产生外部写入。

### 2.4 先完成闭环，再增加 Agent 自主性

首版采用确定的工作流和结构化输出。Agent 用于编排已有工具、解释结果和追问缺失信息，不让自由规划替代业务规则。

## 3. MVP 范围

### 3.1 P0：必须完成

#### 个人档案

- 上传或粘贴简历；
- 支持文本、PDF 和 Overleaf ZIP；
- 提取教育、技能、经历、项目和原始段落位置；
- 管理当前使用的简历版本。

#### JD 导入

- 粘贴 JD 文本；
- 上传 JD 截图；
- 结构化提取公司、职位、职责、硬性要求、加分项、经验和教育要求；
- 保存原始文本和结构化结果。

#### Evidence Matcher

- 将每条 JD 要求匹配到简历证据；
- 区分明确证据、部分相关、无证据和待确认；
- 展示证据原文与来源位置；
- 允许用户纠正匹配结果；
- 汇总技能覆盖和主要风险。

#### 行动建议

- 生成简历表达建议；
- 生成面试准备建议；
- 生成需要补充信息的问题；
- 所有建议必须引用证据或明确说明没有证据。

#### 投递管理

- 一个申请必须关联一个 JD、一个简历版本和可选的匹配结果；
- 支持收藏、已投递、笔试、面试、Offer、接受、拒绝和撤回；
- 记录实际投递日期、下一步行动和备注；
- 状态转换必须遵守状态机。

#### 面试准备

- 根据 JD 和真实经历生成技术、项目深挖、行为和系统设计问题；
- 每道题展示考察点和回答提纲；
- 支持用户输入文字回答；
- 按完整性、真实性、技术正确性和表达结构反馈。

### 3.2 P1：MVP 稳定后完成

- 语音录音、转写、追问和反馈；
- 面试复盘与薄弱项趋势；
- 多简历版本对比；
- PWA 安装与移动端专用导航；
- 结构化评估集和 AI 质量仪表盘；
- 数据导出与删除。

### 3.3 P2：真实用户验证后再决定

- 浏览器扩展导入招聘网页；
- 邮件和日历集成；
- 多用户协作；
- 付费订阅；
- 自动投递或全网职位抓取。

## 4. 核心用户流程

### 4.1 首次使用

1. 用户上传简历。
2. 系统解析并展示个人档案。
3. 用户检查技能、项目和经历是否正确。
4. 用户修正解析错误并设为当前简历。
5. 系统进入“导入第一个岗位”。

验收标准：用户能够在不理解 LaTeX、RAG 或 Agent 的情况下完成首次设置。

### 4.2 岗位分析

1. 用户粘贴 JD 或上传截图。
2. 系统保存原始 JD 并提取结构。
3. 系统把 JD 拆成独立要求。
4. Evidence Matcher 为每条要求寻找简历证据。
5. 用户看到三栏结果：JD 要求、个人证据、建议行动。
6. 用户纠正错误匹配或补充真实经历。
7. 系统生成最终行动清单。

验收标准：任何“已匹配”结论都能点回一段真实简历内容。

### 4.3 简历优化

1. 用户从岗位详情选择一条行动建议。
2. 系统显示原文、建议文本、依据和风险。
3. 用户接受、编辑或拒绝。
4. 系统只修改确认过的段落。
5. 系统展示 Diff 并再次确认。
6. 系统保存新版本，原版本仍可恢复。

验收标准：公司、日期、项目数量和事实性指标不会在没有用户确认时改变。

### 4.4 面试练习

1. 用户在某个岗位详情中进入面试准备。
2. 系统生成基于该 JD 和简历证据的问题。
3. 用户选择文字或语音回答。
4. 系统给出分维度反馈，并引用用户回答和简历证据。
5. 用户保存复盘与下一次练习任务。

验收标准：反馈能够说明哪一句回答存在问题，以及如何基于真实经历改善。

### 4.5 投递跟踪

1. 用户将岗位保存到看板。
2. 系统关联当时使用的简历版本和匹配报告。
3. 用户手动标记已投递，系统此时才记录投递日期。
4. 状态变化产生事件记录。
5. 用户记录面试时间、复盘和下一步行动。

验收标准：历史申请始终能够打开对应 JD、简历版本和匹配结果。

## 5. 信息架构与页面

### 5.1 一级导航

最终导航控制为四项：

1. **工作台**：今日行动、申请概览、待准备面试。
2. **岗位**：已保存职位、岗位详情、证据分析。
3. **面试**：问题、练习、复盘和趋势。
4. **个人档案**：简历版本、项目经历、技能证据和设置。

当前“修改简历”改为岗位详情内的操作；“Agent”保留为实验入口，成熟后融入各页面而不是一级导航。

### 5.2 岗位详情页

桌面端采用三栏：

```text
┌─────────────────┬─────────────────────┬──────────────────┐
│ JD 要求          │ 我的证据             │ AI 建议与行动       │
│ Python / 必须    │ 项目 A · 第 2 条      │ 面试深挖            │
│ RAG / 必须       │ 部分相关 · 待确认      │ 补充实际使用细节      │
│ K8s / 加分       │ 未找到                │ 不写入简历 / 学习计划 │
└─────────────────┴─────────────────────┴──────────────────┘
```

移动端改为逐条要求卡片，按“要求 → 证据 → 行动”纵向显示。

### 5.3 空状态

每个页面必须告诉用户下一步做什么：

- 没有简历：上传或粘贴简历；
- 没有岗位：导入第一份 JD；
- 没有申请：从分析结果加入看板；
- 没有面试记录：选择一个岗位开始练习。

- `suggestions`
- `applications`
- `interview_questions`
- `latex_changes`

第一阶段先修正实体之间的关联和状态一致性，不立即更换数据库。


```text

```

事件表用于恢复时间线和计算真实的转化率，不能只依赖 applications 当前状态。

### 6.5 新增实体：interview_attempts

```text
id
question_id
application_id
answer_text
audio_path
transcript
completeness_score
truthfulness_score
technical_score

```

### 6.6 数据完整性规则

- `match_results.jd_id` 必须对应真实 JD，正常流程中不得为 0。
- `applications.resume_id` 和 `applications.jd_id` 必须对应存在的记录。
- 收藏岗位时 `applied_date` 为空，进入 `applied` 时才写入。
- 终止状态不可继续流转，除非未来增加显式“重新打开”操作。
- 删除被引用记录前必须检查关联，公开版本启用 SQLite 外键。
- AI 原始输出使用合法 JSON 保存，不能使用 Python `str(dict)`。

## 7. AI 设计

### 7.1 逻辑模块

1. **JD Parser**：将输入转成结构化岗位与独立要求。
2. **Resume Parser**：将简历转成可定位的经历证据。
3. **Evidence Matcher**：逐条要求匹配证据。
4. **Career Coach**：基于匹配结果生成行动和改写建议。
5. **Interview Evaluator**：评价用户回答并给出改进。

这些模块先在同一个 Python 服务内实现，通过清晰接口隔离，不拆成微服务。

### 7.2 Evidence Matcher 输出契约

```json
{
  "requirement": "有 RAG 应用开发经验",
  "category": "required",
  "status": "partial",
  "evidence": [
    {
      "text": "使用向量数据库完成文档检索",
      "section": "Projects",
      "entry": "AI Assistant",
      "bullet_index": 1
    }
  ],
  "reasoning": "存在检索实现，但简历没有说明生成、评估或完整 RAG 流程",
  "confidence": 0.78,
  "needs_user_confirmation": true,
  "recommended_action": "询问用户是否实现过生成和评估环节"
}
```

所有模型输出都必须经过 Schema 校验；校验失败时重试一次，仍失败则显示可恢复错误。

### 7.3 Prompt Injection 防护

- JD、简历和网页内容一律视为待分析数据，不作为系统指令执行。
- Prompt 中使用明确的数据边界。
- 工具调用参数由应用代码构造，不直接采用文档中的指令文本。
- 外部内容不得要求系统泄露密钥、读取其他用户数据或绕过确认。

### 7.4 模型路由

不要在业务代码中硬编码具体模型名称。统一按能力选择：

- `fast_structured`：JD 和简历提取；
- `reasoning`：证据匹配和综合分析；
- `vision`：截图解析；
- `speech_to_text`：语音转写；
- `evaluation`：面试回答评价。

供应商和模型名只在配置层定义，界面显示实际使用的能力和供应商。

## 8. 技术架构路线

### 8.1 当前阶段

```text
Streamlit UI
    ↓
Python core / agent / AI client
    ↓
SQLite + ChromaDB + local files
```

适用于单用户本地演示和核心流程验证。

### 8.2 Web MVP 稳定后

```text
Next.js / PWA
    ↓ HTTPS
FastAPI
    ├── Career service
    ├── AI workflow
    ├── File processing worker
    └── Evaluation service
    ↓
PostgreSQL + Object Storage + Vector Store
```

迁移顺序：先从 Streamlit 中抽出服务接口，再替换 UI；不要同时重写前端、后端和数据层。

### 8.3 移动端

第一版优先 PWA，验证下面三个移动场景：

- 上传招聘截图；
- 查看今日面试准备；
- 文字或语音回答问题。

只有在需要系统分享、原生录音、推送通知时再引入 Expo。

## 9. 安全与隐私

简历和面试录音属于敏感个人数据。公开发布前必须完成：

- 登录和资源级用户隔离；
- API 密钥仅保存在服务端；
- 上传文件名净化、路径校验、大小限制、解压总量限制；
- ZIP 路径穿越和压缩炸弹防护；
- 数据导出和删除；
- 日志不记录完整简历、JD、录音或密钥；
- 临时文件自动清理；
- 数据保留期和隐私说明。

当前单用户本地版本应在界面和 README 中明确标注，不能直接作为多用户服务部署。

## 10. 测试与 AI 评估

### 10.1 常规测试

- 单元测试：解析、状态机、路径安全、数据映射；
- 集成测试：简历 + JD → 匹配 → 申请 → 面试题；
- UI 冒烟测试：四条核心用户流程；
- 数据迁移测试：旧数据库升级后记录仍可读取。

### 10.2 AI 测试集

至少准备：

- 30 份脱敏 JD；
- 10 份脱敏简历；
- 100 条人工标注的“要求—证据”样本；
- 正常、模糊、互相矛盾和含恶意指令的输入。

### 10.3 AI 指标

- JD 关键字段提取准确率；
- 要求拆分召回率；
- 证据匹配精确率；
- 虚构内容率；
- 需要用户纠正的比例；
- 相同输入的结果稳定性；
- 单次分析耗时与模型成本。

其中“虚构内容率”是阻断发布的指标，不能只测整体评分是否看起来合理。

## 12. Definition of Done

一个功能只有同时满足以下条件才算完成：

1. 有清晰的用户入口和成功/失败反馈；
2. 数据能够保存并重新加载；
3. 不破坏 JD、简历、匹配和申请之间的关联；
4. 有至少一个正常用例和一个错误用例测试；
5. AI 输出经过 Schema 校验；
6. 涉及简历事实的修改经过用户确认；
7. 手机布局没有阻断性问题；
8. 文档、配置和界面文案与实际实现一致。
